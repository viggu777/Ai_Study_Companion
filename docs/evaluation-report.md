## 1. Executive summary

The core learning loop is fully wired: Space → Project → PDF upload → async extract/chunk/embed/index → project-scoped grounded Tutor with validated citations and a no-LLM insufficient-evidence path → adaptive MCQ plus open-ended quiz with explanatory grading → 0.7/0.3 mastery, ±5 growth, weak-concept recommendations → project/global analytics and a complete 11-view admin console. Live URL serves correctly, tests (241/241), typecheck, lint and build all pass. The recommendation chain code path is now structurally correct with the insert at `services/recommendation.service.ts:380` and chained Inngest events, but no live row was produced during this audit and the chain still depends on event delivery plus a by-design skip when nothing is weak, so it stays PARTIAL. Remaining gaps are reliability polish (serverless-frozen quiz fallback, single-instance limits, unsigned-event exposure), stale docs describing the pre-Gemini stack, and missing reproducibility artifacts (root Dockerfile, HTTP health endpoint).

## 3. Core learning loop walkthrough

Create Space posts to `app/api/spaces/route.ts:18`, scoped by `services/project.service.ts:33`; project creation validates space ownership (`services/project.service.ts:111`) before insert, and the project hub (`app/(app)/projects/[projectId]/page.tsx:33`) fans out to project, ACTIVE recommendations, growth and materials in parallel with per-source catch so one failure never blanks the page. Upload accepts PDF plus images with a 10 MB and non-empty gate (`services/material.service.ts:94`), hashes bytes with SHA-256 (`services/material.service.ts:20`), reuses an existing `(project_id, file_hash)` row as `duplicate:true` instead of a second job, then stores via service-role storage and emits `MATERIAL_UPLOADED` before Inngest send with an inline `processMaterial` fallback. Processing claims atomically from `QUEUED/FAILED` (`services/material.service.ts:397`), downloads, extracts text or OCR, fails documents under 20 chars, chunks, embeds in batches of 20 with a dimension gate, inserts chunks in batches of 50 after deleting stale rows, extracts up to 8 concepts non-fatally, and lands `READY` or `FAILED` with `processing_error` preserved. Tutor (`services/tutor.service.ts:486`) checks project ownership and conversation ownership, dedups within 30 s, persists the user turn, retrieves project-scoped evidence, short-circuits to a persisted fixed insufficient response without calling the LLM, otherwise composes window plus summary plus learning context, calls structured generation at low temperature, filters citations to real chunk IDs and logs the operation. Quiz selection scores concepts by mastery weight, mistake bonus, decline/improve deltas and recency (`services/quiz.service.ts:27`), picks difficulty and MCQ versus open-ended by thresholds, generates validated questions, grades MCQ deterministically and open-ended by LLM with `score>=60` correctness, and only completes when every item is graded. Completion emits `QUIZ_COMPLETED`, sends `quiz/completed`, updates mastery with the 0.7/0.3 rule and history, chains `mastery/updated` into recommendation generation, and surfaces mastery, growth, analytics, recommendations and the dashboard next-action from the same evidence tables, so steps pass data rather than rendering independently. Empty, loading and error states exist on materials, quiz, recommendations and dashboard clients.

## 4. AI/RAG evaluation

Chat defaults to Mercury `mercury-2.5` and falls back to Meta `Llama-4-Maverick-17B-128E-Instruct-FP8` when no Mercury key is set (`lib/ai/AIService.ts:35`), with a 90 s timeout, Mercury headroom and temp clamping, and JSON-mode structured output whose base validator only checks key presence while each feature adds strict validators (quiz requires exactly 4 options with `correct` among them; tutor drops hallucinated chunk IDs and downgrades groundedness). Embeddings are single-provider Gemini `gemini-embedding-001` at 768 dims (`lib/ai/AIService.ts:48`) matching `VECTOR(768)` (`db/schema/006_embeddings_gemini_768.sql:24`), and README plus `.env.example` describe this correctly. Retrieval embeds the query, over-fetches across materials capped at 100, calls `match_chunks(vector(768))`, falls back to a 100-row JS cosine path, filters at 0.25 relevance, balances chunks across files and carries filename, page, chunk ID and similarity into the prompt inside `<retrieved_evidence>` marked untrusted. Grounding is real: insufficient evidence never reaches the LLM, citations are post-filtered to evidence, and excerpts resolve through an ownership-checked chunk endpoint. Quiz and practice generation retry once at lower temperature, shuffle options with unseeded `Math.random`, clamp counts, reuse identical requests within 2 minutes, and rate-limit generation versus submission separately. The main weakness is documentation drift: several docs still describe the retired bge-small-384/Groq stack and therefore misstate thresholds, dimensions and provider behavior.

## 5. Mastery/recommendation evaluation

Mastery averages per-concept question scores then applies `prev*0.7+evidence*0.3` with clamp and rounding (`services/mastery.service.ts:8`), upserts `concept_mastery`, appends `mastery_history` and emits `MASTERY_UPDATED`; skips cover missing questions, missing scores, already-recorded quizzes via `ilike` history check and evidence race (`services/mastery.service.ts:63`). Growth classifies the last two history points with a ±5 threshold (`services/growth.service.ts:6`). The quiz chain is `services/quiz.service.ts:964` send → `lib/jobs/mastery.ts:4` update → `lib/jobs/mastery.ts:16` gate on `updated.length>0` → `lib/jobs/recommendation.ts:4` generate → sole insert `services/recommendation.service.ts:380` into `recommendations` plus `RECOMMENDATION_GENERATED`; practice has a parallel path without the updated gate (`lib/jobs/practice.ts:15`). The previous zero-row symptom is explained, not mysterious: any all-skipped mastery run emits no `mastery/updated`, and `generateRecommendationForProject` returns null when no concept is weak (`score<60` or `REQUIRES_ATTENTION`, missing mastery counted as 0 at `services/recommendation.service.ts:92`), when ownership fails, or when the LLM call throws — so completed quizzes with updated-but-strong mastery correctly produce zero rows by design. No recommendation row was created during this audit because the environment has no prod DB credentials or funded AI keys, so the fix is verified statically and by unit coverage, not by a fresh live row. The Recommendations page itself is healthy: `GET` exists (`app/api/projects/[projectId]/recommendations/route.ts:5`), the client shows skeletons then an explicit empty state (`RecommendationClient.tsx:113`), and `notFound()` fires only for bad or cross-user project IDs (`recommendations/page.tsx:10`), meaning the old not-found report was a routing/ownership case rather than the empty-list bug.

## 6. Data model & security findings

Schema covers users via Supabase Auth plus spaces, projects, materials, chunks (`VECTOR(768)`), concepts, conversations, messages, quizzes, questions, answers, concept mastery and history, recommendations, learning events with an idempotency unique, AI operations, practice, misconceptions and edges (`db/schema/001_initial_schema.sql:5`), with CASCADE deletes, `SET NULL` for quizzed concepts, uniqueness on mastery and idempotency keys, and RLS enabled with `user_id=auth.uid()` plus parent-mediated policies for chunks, concepts, messages and questions (`db/schema/001_initial_schema.sql:224`). Service code never relies on RLS alone: spaces, projects, materials, quiz, tutor conversation and chunk reads all add explicit `user_id` or ownership joins, and misses conflate to 404 so IDs cannot be probed. Storage paths sanitize filenames (`lib/storage/materialStorage.ts:65`) and the private bucket policy checks the UID folder prefix.

### Data isolation

Sampled paths show no IDOR: spaces scope every read by `user_id` (`services/project.service.ts:50`); projects require `id+user_id` (`services/project.service.ts:179`); materials check project ownership on upload and `id+user_id` on list/get/retry/delete (`services/material.service.ts:84`); quiz checks project plus quiz plus user and the question triple (`services/quiz.service.ts:749`); tutor requires project space then conversation `id+project_id+user_id` (`services/tutor.service.ts:372`); chunk excerpts fetch then verify the parent project belongs to the caller (`services/chunk.service.ts:22`); recommendation list and status both scope by `user_id` (`services/recommendation.service.ts:407`). The residual risk is architectural: `getServiceDb()` bypasses RLS and background handlers trust event payloads with only a manual project check, after which concept, quiz, event and chunk reads filter by `project_id` alone, and `processMaterial(materialId)` performs no user check at all, so forged Inngest events are the weakest entry point if signing is not enforced. No secrets are committed: `.env.example` holds empty placeholders, `.gitignore` excludes local env, and key uses are server-only. Prompt-injection hygiene is split: tutor, practice and concept prompts delimit retrieved text as untrusted, while recommendation, quiz and assessment prompts interpolate weak concepts, mistakes and context without that delimiter or rule.

## 7. Document processing evaluation

Upload validates type and size before any DB write, dedups identical bytes per project with SHA-256 including a pre-`010` fallback, and separates duplicate (200, reuse) from fresh (202, new row plus job) at the API boundary. Processing is the strongest pipeline in the repo: atomic `QUEUED/FAILED→PROCESSING` claim prevents Inngest plus inline-fallback double chunks, image OCR versus pdf-parse versus scanned-PDF OCR is selected by file kind, sub-20-char documents fail fast, embeddings run in batches with per-call observability and a dimension gate, chunk replacement deletes before insert for retry safety, concept extraction failure degrades to an empty list instead of a stuck `PROCESSING` state, and every terminal state emits the matching event with `processing_error` retained. Corrupt PDFs pass the header-tolerant upload gate but fail in the job with a visible `FAILED` row, scanned pages have OCR plus tests, large files are rejected synchronously, and retry always reprocesses inline so an accepted-but-never-delivered Inngest event still heals. Remaining polish is quotas (per-file cap only, no per-user quota) and applying `010_material_dedup.sql` to any database created before it.
