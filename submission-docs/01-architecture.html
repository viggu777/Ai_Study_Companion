1. Product overview & the closed learning loop

AI Study Companion is a persistent, contextual, measurable learning workspace — deliberately not a PDF chatbot. A learner organises study into Spaces (broad areas) → Projects (focused goals), uploads Materials (PDFs + images), learns with a grounded AI Tutor, is tested by an adaptive Quiz (MCQ + open-ended), and watches Concept Mastery evolve into Growth Analysis and actionable Recommendations. An Admin Dashboard gives platform-level visibility into users, learning, AI usage, evaluation and system health.

The defining architectural idea is a closed evidence loop: every AI feature either produces learning evidence or acts on it. Nothing stands alone.

Create Space → Create Project → Upload Material → Process & Index → Learn with Tutor (grounded + cited) → Adaptive Quiz → Evaluate → Update Mastery → Analyse Growth → Recommend Next Action → Continue Learning
↺  each step emits events; each event can trigger the next workflow
Design principles: Context-first (never leak across Projects) · Evidence over guessing (say “insufficient evidence” rather than hallucinate) · Persistent-but-relevant context (bounded, not full history) · Asynchronous by design · Observable AI · Controlled AI↔app interaction (validated tools, never raw DB access).

3. High-level architecture

👤 User → HTTPS (Vercel) → Next.js 14 App (UI + thin Route Handlers)
↓ synchronous   ·   ↓ emits events
🧩 Service Layer (ownership + business logic — services/*.ts)   ⇄   ⚙️ Inngest jobs (material / mastery / recommendation / practice — lib/jobs, /api/inngest)
↓
🤖 AIService (Mercury chat/structured/eval + Gemini embeddings — lib/ai/AIService.ts)   ⇄   🗄️ Supabase Postgres + pgvector + RLS → 📦 Storage (PDFs)
↓ cross-cutting: Observability (ai_operations) · Events (learning_events) · Evaluation (18 fixtures + run history)

Golden rule: every request — sync or background — passes Authentication → Authorization → Ownership validation → Business logic → Database (RLS as second layer) before any data is touched.

6. Database & data isolation

One Postgres holds relational + vector data. Simplified schema (uuid PKs, timestamptz, CASCADE to parents):

spaces (id, user_id, name, description)
projects (id, space_id, user_id, name, description, learning_goal)
materials (id, project_id, user_id, filename, storage_path, file_hash, file_size,
           status QUEUED|PROCESSING|READY|FAILED, page_count, processing_error)
chunks (id, material_id, project_id, content, page_number, chunk_index,
        embedding VECTOR(768), metadata JSONB)
concepts (id, project_id, name, description, source_material_id)
concept_mastery (id, project_id, concept_id, user_id, mastery_score, evidence JSONB)
mastery_history (id, concept_id, user_id, previous_score, new_score, reason)  -- growth input
conversations (id, project_id, user_id, summary, summary_updated_at, pinned) / messages (…, citations JSONB)
quizzes / questions (MCQ|OPEN_ENDED, difficulty, options, correct_answer, explanation)
answers (response, is_correct, score, evaluation JSONB)
practice_assignments / practice_items / misconceptions (repeated-mistake tracking)
recommendations (title, action_items JSONB, ACTIVE|COMPLETED|DISMISSED)
learning_events (user/space/project, event_type, entity, metadata)  -- activity + analytics + admin
ai_operations (feature, model, request_id, latency_ms, success, tokens, cost, error)

Isolation (defence in depth): service functions scope every lookup — WHERE id=$1 AND user_id=$2, never bare id; misses return 404 (no existence leak); RLS user_id = auth.uid() on all user tables as an independent second layer; background jobs carry user_id/project_id in the event payload; retrieval filters WHERE project_id always. Migrations 001→014 apply in order (npm run migrate or SQL editor); indexes on all FKs, learning_events(project_id, created_at), and hnsw/ivfflat on chunks.embedding.

7. RAG & grounded Tutor

7.1 Indexing pipeline (async)

Upload (PDF/png/jpg/webp, 10 MB, non-empty, SHA-256 dedupe per project) → Storage → materials QUEUED → Inngest job (inline fallback)
↓
Claim (atomic QUEUED/FAILED→PROCESSING) → extract text w/ page numbers (pdf-parse; OCR for scans) → reject <20 chars → chunk (~2400 chars / 320 overlap) → Gemini embed (batches of 20, dim-gated) → insert (batches of 50, stale deleted) → concepts (≤8, non-fatal) → READY / FAILED+error

7.2 Tutor query path

Authenticate → validate project ownership → dedupe (30 s) → persist user turn → embed query (Gemini, 10-min cache) → match_chunks scoped by project_id (over-fetch ≤100, JS-cosine fallback) → filter RELEVANCE_THRESHOLD=0.25, balance across materials, top-K 5
↓
Insufficient evidence? → skip LLM, persist fixed “couldn't find enough evidence…” response  ·  Else → compose (chunks + 6-msg window + rolling summary + learning/assessment context) → generateStructured (Mercury, low temp) → validate schema + filter citations to real chunk IDs → persist + log
Citations: every grounded answer returns {answer, confidence, grounded, citations[{materialId, materialName, page, chunkId}], followUp}; UI shows “Source: Name — Page N” with excerpts via ownership-checked /api/chunks/[id].
Prompt-injection defense: retrieved text is data inside a delimited <retrieved_evidence> block marked untrusted; system prompts forbid following instructions inside it. Verified by fixture TUTOR-05 (malicious PDF).

8. Adaptive quiz, assessment, mastery, growth & recommendations

CapabilityHow it works (shipped)
Adaptive selectionWeighted score per concept: low mastery + recent mistakes + decline/improve deltas + recency/frequency (anti-repeat); difficulty + MCQ-vs-open-ended picked by thresholds — never naive wrong→easy.
GenerationMercury structured output {concept_id, type, difficulty, question, options[4], correct_answer, explanation}; server validation (exactly 4 options, correct ∈ options); retry once at lower temp; 2-min duplicate-quiz guard; answer gating (correct/explanation hidden until graded).
GradingMCQ deterministic string compare (no LLM). Open-ended: LLM → {score 0–100, understanding, strengths, missingConcepts, reasoningQuality, feedback}; score ≥ 60 ⇒ correct; failure raises, never writes a guess; per-question idempotency (re-POST returns existing).
Mastery (deterministic)new = prev × 0.7 + evidence × 0.3 (MCQ 0/100, open-ended as-is, averaged per concept), clamped/rounded; upsert + mastery_history row + MASTERY_UPDATED. The LLM never sets a score.
GrowthLast two history points per concept: >+5 IMPROVING, <−5 REQUIRES_ATTENTION, else STABLE.
RecommendationsAfter mastery updates: weak concepts (score<60 or REQUIRES_ATTENTION) + mistakes + goal + activity → Mercury → {title, action_items[2–5]} naming real concepts/materials; skipped when nothing is weak; COMPLETED/DISMISSED lifecycle.

Differentiators on top of the baseline: Flashcards (weak-concept decks), Deep Practice (sections + MCQ), Misconception tracking (repeated-mistake workflow), Knowledge Graph, Sub-concept expansion, conversation pinning.

9. Persistent learning context

Only useful context is stored or sent — never full transcripts:

Request → Project Knowledge (RAG chunks = evidence) + Conversation (last 6 msgs, always) + Rolling Summary (older turns, ≤1200 chars, refreshed ~every 6 msgs past 8) + Learning Context (goal, weak concepts, repeated mistakes) + Assessment Context (recent quiz/answers) → Compose → LLM

Summary is context-only (never evidence, never instructions) and refresh is best-effort — it never blocks the answer. This is what separates a companion from a chatbot.

10. Events & intelligent background workflows

One learning_events table powers the activity feed, analytics, recommendations and admin. Catalog includes SPACE/CREATED, PROJECT_CREATED, MATERIAL_UPLOADED/PROCESSING_STARTED/READY/FAILED, TUTOR_MESSAGE_SENT/RESPONSE_GENERATED, QUIZ_STARTED, QUESTION_ANSWERED, QUIZ_COMPLETED, MASTERY_UPDATED, RECOMMENDATION_GENERATED/COMPLETED (+ practice/misconception events).

Material: Upload → Process → Chunk → Embed → Concepts → READY
Learning: Quiz Completed → Evaluate → Update Mastery → Detect Weakness → Insight → Recommend
Repeated-mistake: Pattern (misconception bump/merge) → Update Context → Targeted Recommendation

Idempotency & recovery: atomic material claim; file-hash dedupe (duplicate → reuse, no second job); 2-min quiz-generation guard; per-question answer idempotency incl. concurrent-race handling; unique constraint where duplication harms; FAILED materials retry inline (heals even if Inngest delivery failed); user never needs the browser open.

11. AI engineering, observability & evaluation

AI is treated as an engineered system: one AIService abstraction (chat / structured / embeddings / evaluation / doc-understanding), JSON-mode + per-feature validators, 90 s timeouts, typed fallbacks.

Observability: every call writes one ai_operations row — feature, model, request_id, latency_ms, success, tokens, estimated_cost, error — for TUTOR, CONVERSATION_SUMMARY, EMBEDDING, QUIZ_GENERATION, OPEN_ENDED_EVALUATION, CONCEPT_EXTRACTION, RECOMMENDATION, FLASHCARD_GENERATION, SUBCONCEPT_GENERATION (+ practice). Surfaced in /admin/ai-usage and project/global analytics — answering why slow? which model? why poor retrieval? which workflow failed? what cost?

Evaluation: 18 curated fixtures (tests/eval/fixtures.ts) — Tutor (grounded / unsupported / multi-concept / citation / injection), Retrieval (query→expected source), Assessment (missing-concept detection), Recommendations (specificity rubric). npm run eval stamps runId/suiteVersion, archives per-run history, and /admin/ai-evaluation shows run-over-run IMPROVED REGRESSED UNCHANGED BASELINE. Regression-aware by design: prompt/model/retrieval changes are diffed, not silently shipped.

12. Reliability, security & performance

RiskHandling (shipped)
AI timeout / provider failure90 s timeout; retry once w/ backoff; typed user-safe error; UI never stuck on Loading.
Invalid AI outputSchema reject + log (success=false) + safe fallback; open-ended grading raises instead of persisting guesses.
PDF / retrieval failureFAILED + processing_error + Retry; empty retrieval = insufficient-evidence path, not an error.
Auth / ownershipRoutes: 401 unauthenticated, 404 not-owned (no leak); pages redirect to /login; writes scoped by user_id.
Cost spikesIn-memory per-user fixed windows (tutor 20/min, quiz-gen 5/min, quiz-submit 60/min, flashcards 5/min, subconcepts 10/min) → 429 + Retry-After; embeddings cached 10 min; no re-embed of READY materials.
Duplicates on retryHash dedupe, atomic claims, idempotent answers, generation guards — retries never duplicate state.

Performance (prototype-appropriate): pgvector top-K + threshold (no full scans in app code); balanced-per-material retrieval; paginated analytics/admin; async everything long-running; no unnecessary AI calls (summary best-effort, embeddings only for real work). Streaming Tutor and response caching are documented future work, not regressions.

13. Deployment & configuration

Vercel (Next.js app, /api/inngest synced to Inngest Cloud)  +  Supabase (Postgres/pgvector, Auth, private materials bucket)  +  Inngest (jobs)  +  Mercury + Gemini (AI)

Setup: import repo → set env (see .env.example: DATABASE_URL, NEXT_PUBLIC_SUPABASE_URL/ANON_KEY, SUPABASE_SERVICE_ROLE_KEY (server-only), MERCURY_API_KEY/BASE_URL/CHAT_MODEL, GEMINI_API_KEY/MODEL/DIM, INNGEST_EVENT/SIGNING_KEY (+DEV=1 local), ADMIN_EMAILS/ADMIN_USER_IDS) → run migrations 001→014 → ensure bucket → sync Inngest → smoke-test the full loop live. Secrets are env-only, gitignored, never committed; service-role key never reaches the browser.
